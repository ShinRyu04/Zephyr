## 2. Yang KURANG dan temuan (dengan bukti)

Semua temuan di bawah adalah **kelemahan jalur SSH yang ada sekarang**, bukan usulan.
Tidak ada satu pun yang diperbaiki di sini karena semuanya berada di berkas milik lane lain.

### T1 — `ssh_connect` tidak memancarkan satu pun opsi keamanan (tinggi, jalur interaktif)
`ssh.rs:265–273` menyusun argv `['-p', port, 'user@host']` dan menyisipkan `-i keyPath`
(271–272). Tidak ada `BatchMode`, `StrictHostKeyChecking`, `UserKnownHostsFile`,
`ConnectTimeout`, atau `-F`. Akibatnya jalur yang benar-benar dipakai manusia ini
memakai `~/.ssh/config` dan `known_hosts` milik user, menerima host key baru menurut
kebijakan bawaan ssh, dan bisa menggantung pada prompt agen/passphrase tanpa batas waktu.
Bukti positif di jalur yang sama: `auth == 'password'` tidak menaruh apa pun di argv —
kata sandi hanya muncul di prompt PTY. Itu **benar** dan dipertahankan modul baru.

### T2 — token target berawalan `-` dibaca ssh sebagai OPSI (tinggi)
`ssh.rs:268` memakai `format!("{}@{}", cfg.user, cfg.host)`; `sftp.rs:124–128` (di dalam
`sftp_batch`, **jalur hidup**) memakai `if user.is_empty() { host } else { format!("{user}@{host}") }`.
Catatan supaya tidak salah sasaran: `args_umum()` (`sftp.rs:85–102`) memuat pola yang sama,
tetapi fungsi itu **hanya dipakai oleh unit test** (358, 365) — bukan jalur produksi; jalur
SFTP yang benar-benar dipakai adalah `sftp_batch` (124–128) dan pembangun skrip di `sftp_list`
(205–212). `sftp_tunnel_start` menyusun `ssh`-nya sendiri dengan `-p <port>` (281–282), dan
`-p` memang benar untuk `ssh` (yang salah adalah `-P`: dipakai `sftp` di 122).
Karena `validate()` hanya memeriksa *kosong* (host 75, user 81), sebuah konfigurasi dengan
`user = "-oProxyCommand=…"` menghasilkan token `-oProxyCommand=…@host` yang **dibaca ssh
sebagai opsi**, bukan sebagai tujuan. Di `sftp_batch` vektor yang sama bisa datang dari `host`
sendiri lewat cabang `user.is_empty()`.
Terverifikasi pada ssh nyata (OpenSSH_10.2p1) di mesin ini: satu token `-oProxyCommand=…`
sebagai pengganti host membuat ssh mencetak **usage** (token dikonsumsi sebagai opsi sehingga
tidak ada host tersisa) — jadi bukan eksekusi langsung, tetapi opsi lain seperti `-F`,
`-i`, `-o UserKnownHostsFile=/dev/null`, dan `-E <logfile>` tetap bisa disuntikkan.
Nota: `-i` lalu `keyPath` di `ssh.rs:270–273` **aman** karena `-i` mengambil argumen
berikutnya apa pun isinya; nilai berawalan `-` di posisi itu tidak menjadi opsi.

### T3 — `sftp_list` menyisipkan `path` mentah ke bahasa batch SFTP (tinggi)
`sftp.rs:205–212` membentuk `ls -l {path}\n` dari `path.trim()` tanpa escape, lalu
`sftp_batch` menulisnya ke stdin `sftp -b -` (139). Bahasa batch SFTP berganti perintah
**per baris**, jadi satu `\n` di dalam `path` menambahkan perintah kedua (`put`, `get`,
`rm`, `rename`, …) yang dieksekusi di host tujuan, melewati seluruh pemeriksaan yang
ditujukan ke satu `ls`. Tidak ada demo hidup untuk ini karena butuh server SFTP; buktinya
adalah dua baris statis di atas (interpolasi mentah + penulisan ke stdin skrip).
Gerbang yang sudah tersedia dan bisa dipakai untuk menutupnya: `periksaPerintahShell()`
(`agentGuard.ts:267` menolak CR/LF) — lihat §7.

### T4 — host key tidak pernah di-pin dan tidak dicatat di berkas milik app (sedang)
`sftp.rs:85–102` tidak menetapkan `UserKnownHostsFile`, jadi catatan host key SFTP masuk
ke `known_hosts` **milik user**; `StrictHostKeyChecking=accept-new` diterima pada
pertemuan pertama. Tidak ada tempat mana pun yang menyimpan fingerprint yang sudah
disetujui, sehingga "sudah pernah dilihat user" tidak bisa dibedakan dari "tidak pernah".
Modul baru menutup ini di sisi argumen (`hostKeyPolicy: 'pin'` **wajib** membawa
fingerprint yang sah, dan `'pin'` memancarkan `StrictHostKeyChecking=yes`), tetapi
datanya belum ada di `ssh.json` — itu bagian §7 dan §6.

### T5 — log tidak menyaring rahasia (sedang)
`logging.rs:49` (`write_line`) menulis baris apa adanya; `ssh.rs`/`sftp.rs` mengembalikan
stdout/stderr mentah (mis. `sftp_batch` → `Ok(String::from_utf8_lossy(&out.stdout)…)`, 151).
`sshpass`, prompt `passphrase`, dan pesan `-o ProxyCommand` yang gagal adalah bentuk yang
wajar muncul di sana. Penyaringnya sekarang tersedia: `sshRedaksi.ts`.

### T6 — `port` di Rust tidak pernah melebihi 65535; lapisan TS tetap harus memeriksa
`port: u16` membuat "port 70000" mustahil sampai ke `validate()`. Pemeriksaan rentang
di `sshArgv.ts` tetap perlu karena argumen tool datang dari model sebagai JSON bebas
(`"22"`, `0`, `70000`, `-1`), dan `port: 0` di `ssh.rs:78` hanya tertangkap untuk CRUD,
bukan untuk pemanggilan `sftp_*` (yang memakai `port.unwrap_or(22)`, `sftp.rs:204`).

## 3. Modul baru: kontrak yang dikunci dan diuji

`src/lib/sshArgv.ts` — **murni**, tanpa `fs`, tanpa jaringan, tanpa AST Zephyr apa pun;
bisa diuji di Node polos (itulah yang dilakukan harness).

```ts
export type ModeSsh = 'ssh' | 'scp' | 'sftp';
export type KebijakanHostKey = 'accept-new' | 'pin';
export interface TargetSsh { id; host; user; port: number; auth: 'key'|'password';
                             keyPath?; hostKeyPolicy?: KebijakanHostKey; fingerprint? }
export interface OpsiSsh { knownHostsFile: string; configFile: string;
                           connectTimeoutMs?; serverAliveIntervalSec?; serverAliveCountMax?;
                           gunakanAgen?: boolean; opsiTambahan?: Record<string,string> }
export interface JalurSsh { bin: ModeSsh; argv: string[] }

susunArgv(t, o, mode='ssh'): string[]        // inti: selalu daftar, tidak pernah string shell
susunJalur(t, o, mode?): JalurSsh
susunArgvJalankan(t, o, perintah: readonly string[]): { bin; argv; perintah }   // token dikutip
susunArgvSkripMentah(t, o, skrip: string): JalurSsh                            // 1 token verbatim
susunArgvSalin(t, o, sumber, tujuan): JalurSsh
teksArgv(bin, argv): string                  // KHUSUS tampilan/log
jagaArgv(argv): void                         // lempar 'rahasia-di-argv' sebelum argv dipakai
targetMembawaRahasia(t): boolean
validasiTarget(t): KodeGalatSsh[]            // melaporkan SEMUA galat, bukan yang pertama
hostSah/userSah/portSah/kunciSah/fingerprintSah/berkasOpsiSah
GalatSsh, KodeGalatSsh, PORT_MIN/PORT_MAX, TIMEOUT_MS_*, OPSI_DIIZINKAN, OPSI_DILARANG,
FIELD_TERLARANG_DI_TARGET
```

Aturan yang **dikunci** (masing-masing punya kasus uji):

1. **Keluarannya daftar argumen, bukan string shell.** Tidak ada satu pun cabang yang
   menggabungkan perintah menjadi satu string; penggabungan hanya ada di `teksArgv()` yang
   tidak boleh dipakai untuk menjalankan apa pun. `;`, `&&`, `|`, kutip, dan spasi karena itu
   tidak bisa memecah perintah.
2. **Perintah user tidak pernah menyatu dengan argv ssh.** `susunArgvJalankan` mengutip satu
   token menjadi satu elemen; `susunArgvSkripMentah` menaruh skrip sebagai satu elemen
   verbatim. Dua-duanya tidak menambah elemen argv karena karakter di dalam perintah.
3. **Opsi keamanan selalu dipancarkan dan tidak bisa ditimpa.** Urutan: semua `-o` keamanan
   dulu → opsi pemanggil yang masuk `OPSI_DIIZINKAN` → `-F <config app>` → `-i <kunci>` →
   `-p`/`-P <port>` → `user@host` → perintah. Alasan urutan ini terukur, bukan teoretis:
   OpenSSH memakai nilai **pertama** yang diperoleh untuk opsi seperti ini, dan `-o` di baris
   perintah mengalahkan berkas config. Bukti (§8, blok INFO): config yang berisi
   `StrictHostKeyChecking no` + `BatchMode no` + `UserKnownHostsFile /tmp/other` tetap
   terpantul sebagai `accept-new` / `yes` / berkas app kita.
   Bawaan: `BatchMode=yes`, `StrictHostKeyChecking=accept-new`, `UserKnownHostsFile=<app>`,
   `ConnectTimeout=20`, `ServerAliveInterval=15`, `ServerAliveCountMax=3`, `TCPKeepAlive=yes`,
   `IdentityAgent=none`, `IdentitiesOnly=yes` (untuk auth key), `-F <config app>`.
   `StrictHostKeyChecking=no` tidak pernah dihasilkan untuk mode apa pun.
4. **Rahasial tidak pernah masuk argv.** Field `password`/`passphrase` pada target diabaikan;
   `jagaArgv()` menolak argv yang memuat kata sandi atau blok kunci privat. Uji nyata
   memakai canary: canary tidak muncul di `argv.join(' ')` (lihat §8).
5. **Nilai `-o` berspasi dikutip.** Terukur: `-o UserKnownHostsFile=/a b/kh` tanpa kutip
   membuat ssh memotong nilainya di spasi menjadi `/a` — berkas known_hosts yang salah,
   **tanpa galat yang terlihat**. Karena itu nilai yang memuat spasi dibungkus `"` di dalam
   token; nilai yang sudah memuat `"` ditolak (ambigu).
6. **Host/user/port/kunci divalidasi ketat**: host per-label (label kosong `a..b`, label >63,
   host >253, spasi, `;`, `$`, backtick, dan tanda `-` di awal/akhir ditolak; `_` diizinkan
   untuk host internal; IPv6 lewat jalur terpisah, bentuk berkurung `[::1]` **ditolak** dan
   ssh dipanggil dengan `::1` polos); user maks 64 tanpa `@`/`:`/spasi dan tanpa awalan `-`;
   `port` harus bilangan bulat 1–65535; `keyPath` non-kosong, ≤4096, tanpa karakter kontrol,
   dan tanpa awalan `-`; fingerprint wajib `SHA256:` + 43 base64 (+ `=` opsional).
7. **Host key tidak dipercaya otomatis tanpa catatan.** `hostKeyPolicy: 'pin'` **wajib**
   membawa fingerprint yang valid; tanpa itu `susunArgv` melempar `fingerprint-tidak-sah`.
   `'pin'` memancarkan `StrictHostKeyChecking=yes`; `'accept-new'` adalah bawaan yang jujur
   (menerima pada pertemuan pertama) dan tidak berpura-pura tahu.
8. **Daftar tolak untuk opsi pemanggil**: `ProxyCommand`, `LocalCommand`, `PermitLocalCommand`,
   `KnownHostsCommand`, `ProxyJump`, `ProxyUseFdpass`, `IdentityAgent`, `UserKnownHostsFile`,
   `StrictHostKeyChecking`, `BatchMode`, `IdentityFile`, `SendEnv`, `SetEnv`, `RemoteCommand`
   (cocok tanpa peduli huruf besar-kecil), ditambah tolak-semua untuk kunci di luar
   `OPSI_DIIZINKAN`. Tanpa ini, pemanggil bisa membatalkan opsi keamanan kita dari luar.
9. **`sshRedaksi.ts` tidak menggantikan apa pun.** Ia melengkapi `redaksi()` di
   `konteksZephyr.ts:168`: yang lama menyaring konteks untuk **model** (API key, `.env`,
   nama berkas rahasia), yang baru menyaring **keluaran proses SSH dan log** (blok kunci
   privat multi-baris, `sshpass -p`, `-pw`, kredensial di URL, header `Authorization`,
   JWT, token populer). Prinsipnya sama: hanya **nilai** yang diganti, bentuk kalimat tetap
   terbaca, dan rahasia tidak pernah dikembalikan. Dua aturan di `sshRedaksi.ts` lahir dari
   kegagalan uji yang nyata, bukan dari teori: header `Authorization: Bearer <token>`
   (tidak tertangkap aturan penugasan karena tidak ada `=`/`:`) dan `-pw <rahasia>` sebagai
   **dua token argv** (penyensoran per-token tidak cukup; `sensorArgv` mengganti token yang
   tepat berada setelah flag kata sandi, sementara `-P` port scp sengaja tidak dianggap flag).

**Yang TIDAK BOLEH masuk log** — daftar ini diekspor sebagai `DILARANG_LOG` (12 butir) dan
harus dibaca sebelum menambah satu `write_line()` baru:

1. kata sandi SSH apa pun isinya, termasuk yang tersimpan di `ssh.json`;
2. passphrase kunci privat;
3. isi berkas kunci privat (PEM/OPENSSH), termasuk satu baris body base64-nya;
4. nilai `password_enc`/`passwordEnc` dari `ssh.json`;
5. nilai apa pun yang diawali `password=`, `passwd=`, `passphrase=`, `-pw `, `sshpass -p`;
6. header `Authorization` (Bearer/Basic) dan token sesi;
7. token API pihak ketiga (`gh*_`, `github_pat_`, `sk-`, `AKIA`, `xox*`);
8. argv apa pun yang memuat kata sandi — argv bisa dibaca proses lain;
9. isi mentah `.env` / `secrets.json` / `credentials.json`;
10. perintah remote yang memuat rahasia (`export TOKEN=…`): sensor dulu, baru log;
11. isian variabel lingkungan proses ssh;
12. body base64 kunci privat yang muncul **tanpa** baris BEGIN/END (tidak bisa dikenali pasti —
    karena itu jangan sampai masuk log).

Yang **boleh** (`BOLEH_LOG`, 5 butir): fingerprint host key `SHA256:…`, `user@host` dan port,
path berkas kunci (metadata, bukan isinya), kode keluar/durasi/jumlah baris, dan pesan galat
ssh yang sudah disensor. Dua daftar ini ada supaya aturannya tidak berubah menjadi larangan
selebar mungkin — fingerprint justru **harus** dicatat agar perubahan host key terlihat.

## 4. Keputusan penyimpanan kunci (apa adanya)

**Kunci privat: tetap berkas milik user; app hanya menyimpan PATH-nya.** Itu sudah keadaan
sekarang (`ssh.rs:89–93` menyimpan `key_path`; `ssh_connect` menyuntikkan `-i` di 270–273) dan
keputusan lane ini adalah **mempertahankannya**. Menyalin kunci privat ke dalam data app akan
menggandakan permukaan rahasia tanpa menambah keamanan; `keyPath` juga satu-satunya bentuk yang
tetap bekerja dengan `ssh-agent`, hardware key, dan berkas yang hanya bisa dibaca user.

**Passphrase/kata sandi: `password_enc` di `ssh.json` adalah OBFUSCATION, bukan enkripsi
yang melindungi.** `secrets.rs` menurunkan keystream dari `machine_seed()` (10) dan
meng-XOR-nya (45), lalu base64 (52). Siapa pun yang bisa membaca `ssh.json` **dan** menjalankan
kode di mesin yang sama (atau membaca `machine_seed`, yang berasal dari mesin, bukan dari
rahasia user) bisa mengembalikan isinya. Ini bukan keyring OS: tidak ada DPAPI/Credential
Manager, tidak ada master password, tidak ada isolasi per-user OS.
Ditulis apa adanya supaya tidak ada yang menyimpulkan "password terenkripsi" berarti
"password aman". Rencana: pindahkan ke **Windows Credential Manager** (crate `keyring`)
sehingga `ssh.json` hanya menyimpan metadata; `ssh.rs:211` menjadi satu-satunya titik yang
berubah. Itu **bukan** bagian lane ini dan tidak dikerjakan di sini.

**Host key (known_hosts & pin fingerprint).** Keputusan: berkas known_hosts **milik app**
(`UserKnownHostsFile=<app>/known_hosts`, opsi sekarang wajib dan sudah dipancarkan modul),
plus kolom `fingerprint` per-target di `ssh.json` untuk mode `pin`. Alasannya: kalau catatan
host key bercampur dengan `known_hosts` milik user, perubahan host key pada koneksi app
tercampur dengan percobaan manual user di terminal lain, dan `accept-new` menutupinya dengan
menerima begitu saja. Dengan berkas terpisah, "app ini pernah melihat host key ini" punya
jawaban tunggal dan bisa ditampilkan pada kali pertama.
`~/.ssh/config` juga tidak dibaca lagi (`-F <config app>`) supaya `ProxyCommand`,
`LocalCommand`, dan `UserKnownHostsFile` yang dibuat manusia tidak diam-diam berlaku pada
jalur otomatis. Ini perubahan perilaku yang harus disadari: host yang hanya ada di
`~/.ssh/config` user (mis. alias dengan `HostName`/`Port`) **tidak** akan dikenali lagi —
karena itu entri target di `ssh.json` harus berdiri sendiri (host, port, user eksplisit).

## 5. Izin yang harus diminta ke pengguna

Semuanya **per-target**, tidak ada wildcard. `ssh` sudah dideklarasikan berefek `exec` di
`catalog.ts:177` (kolom butuh-izin `true`), jadi izin ini bukan kategori baru — yang baru
adalah bentuknya:

1. **Koneksi pertama ke sebuah `id`**: tampilkan `user@host:port`, auth (`key`/`password`),
   dan **fingerprint host key** yang diterima; minta konfirmasi. Setelah disetujui, simpan
   fingerprint itu pada entri `ssh.json` → target naik ke `hostKeyPolicy: 'pin'`. Selama
   belum di-pin, `run` **ditolak** (bukan diam-diam `accept-new`).
2. **Menjalankan perintah (`action=run`)**: minta izin per panggilan pertama pada sesi, dan
   selalu tampilkan perintahnya utuh. Perintah satu baris (CR/LF ditolak oleh
   `periksaPerintahShell`), panjang dibatasi, `timeoutMs` dibatasi 1_000–300_000.
3. **Auth `password`**: izin terpisah untuk **setiap** pemanggilan `run`, karena kata sandi
   yang di-`sshpass` berarti rahasia berada di memori proses anak (dan bisa terlihat lewat
   daftar proses bila `sshpass` tidak dipakai dengan benar). Jalur `ssh_connect` (PTY) tetap
   `password` lewat prompt — itu tidak berubah dan tidak butuh izin baru.
4. **Menonton keluaran**: keluaran `run` masuk ke model **setelah** `sensorUntukLog()`.
   Pemotongan (`batas` 8000) harus disebut saat menampilkan, supaya model tahu ada bagian
   yang tidak dibaca.
5. **Menyimpan kata sandi** (`ssh_save_password`) tetap izin eksplisit user di UI setelan,
   dengan peringatan jujur bahwa penyimpanannya baru setara obfuscation (§4).
6. Kalau *host key berubah* untuk target yang sudah di-pin: **tidak ada izin otomatis**.
   Tolak koneksi, tampilkan fingerprint lama vs baru, dan minta keputusan user.

Catatan penting untuk penulis tambalan:

- `periksaPerintah` sudah diimpor di `mcp.ts:62` (`from './builtins'`), tidak perlu impor baru.
- `cmd.sshExec` **belum ada**: itu perintah Rust baru yang harus ditambahkan di `ssh.rs`
  (bukan lane ini). Bentuk yang diusulkan: `ssh_exec(target_id, argv: Vec<String>, skrip: String,
  timeout_ms: u16) -> { stdout, stderr, code, durasi_ms }` — mengambil argv dari modul ini
  **apa adanya** (jangan menyusun ulang di Rust, jangan menyisipkan apa pun), menyuntikkan argv
  sebagai daftar ke `crate::proc::cmd()` (bukan shell), dengan `stdin` piped untuk menerima
  skrip. Kata sandi tidak pernah lewat argv: untuk auth `password`, lewat `sshpass` dengan
  `-e`/`SSHPASS` di lingkungan anak dan **segera** dihapus setelah spawn.
- `opsiSshApp()` = `{ knownHostsFile: <appdata>/zephyr/known_hosts, configFile: <appdata>/zephyr/ssh_config }`.
  Frontend sudah punya jalur `%APPDATA%\zephyr\` (lihat `commands.ts:198`); kalau tidak
  eksis sebagai fungsi publik, tambahkan perintah Rust `ssh_paths()` — **jangan** menebak
  jalurnya di dua tempat berbeda.
- Jangan tambahkan tool baru (`mcp__zephyr__ssh_exec`): pertahankan satu tool dengan `action`
  yang bertambah, supaya anggaran tool per giliran tidak naik.
- `connect` sengaja **tidak** dialihkan ke jalur baru ini: PTY adalah untuk manusia, dan

| Percobaan | Hasil terukur |
|---|---|
| `-o UserKnownHostsFile=/a b/kh` (token tanpa kutip) | dipotong diam-diam menjadi `/a` → berkas known_hosts salah, tanpa galat |
| `-o 'UserKnownHostsFile="/a b/kh"'` (dikutip di dalam token) | nilai utuh, berlaku |
| token host `-oProxyCommand=touch <marker>` | ssh mencetak **usage**; marker tidak dibuat (opsi dikonsumsi, host hilang) |

| `-o StrictHostKeyChecking=no` lewat `-G` | **diterima** ssh → alasan kita tidak boleh sekadar "percaya pemanggil" |
| `ssh -F <berkas kosong>` / `<berkas tidak ada>` | diterima; `-G` tetap memantulkan opsi kita |
